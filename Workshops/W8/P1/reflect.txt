In Workshop 8:
In my code, the iAccount interface contains pure virtual functions like 
credit(), debit(), monthEnd(), and display(). 
This use of pure virtual functions mandates that any class deriving from iAccount must provide
implementations for these functions, thus enforcing a contract for behavior among all account types.
The iAccount class in my code is an abstract base class. 
It provides a common interface for all account types (SavingsAccount and ChequingAccount) 
but cannot be instantiated directly. 
Abstract base classes are foundational in designing a polymorphic class hierarchy, 
where they define a common interface for all derived classes.
In my code, SavingsAccount and ChequingAccount are concrete classes that inherit from iAccount and provide specific 
implementations for the pure virtual functions credit(), debit(), monthEnd(), and display()
An abstract base class, cannot be instantiated directly and is intended to provide a 
template or contract for its derived classes. 
It often includes pure virtual functions without implementations. 
A concrete class, on the other hand, is a class that can be instantiated and typically provides
 implementations for all its member functions. 
In Ms3:
In the context of my Patient class, while it doesn't define an abstract class by the strictest definition, 
it lays the groundwork for polymorphic behavior and could easily be adapted into an abstract class by introducing
pure virtual functions. 
For instance, if the healthcare system needed to differentiate between different types of patients
with unique behaviors (like WalkinPatient, AppointmentPatient, etc.), you could define common interfaces as 
pure virtual functions in Patient, making it abstract.
